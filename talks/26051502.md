# Phase 1 复检报告（二次）

## 结论

当前 Phase 1 比上一次稳定不少，核心链路已经能跑通，服务端测试也通过了。但实现里仍然有几个会直接影响真实使用体验的问题，主要集中在 VS Code 渲染清理、多变更事件处理，以及当前补上的“多步 rename”启发式边界仍然偏宽这三块。

## Findings

### 1. 高亮清理只作用于当前活动编辑器，切换标签页后会残留脏装饰

文件：[/Users/xushengni/project/github/nextone/editors/vscode/src/extension.ts](/Users/xushengni/project/github/nextone/editors/vscode/src/extension.ts#L246)

`clearSuggestion()` 只对 `vscode.window.activeTextEditor` 调用 `setDecorations([], [])`。但 suggestion 是渲染在“当时的活动 editor”上的，之后如果用户切换到别的标签页，再收到 `cancelSuggestion`、自动失效或手动 reject，清理逻辑会作用在新的活动 editor 上，旧 editor 上的红绿高亮会残留。

这会导致非常直接的 UI 错乱：suggestion 实际已经失效，但旧文件里还留着高亮，看起来像一个仍可接受的建议。应当把 suggestion 绑定到具体 `TextEditor` 或 `uri`，清理时显式找到原始渲染目标，而不是依赖当前活动 editor。

### 2. 服务端对一次 `didChange` 里的多处变更只提取第一处，历史记录会失真

文件：[/Users/xushengni/project/github/nextone/server/src/next_edit_server/server.py](/Users/xushengni/project/github/nextone/server/src/next_edit_server/server.py#L258)

当前 `_handle_did_change()` 在 `p.changes` 长度大于 1 时只记录第一条 change 的 `old_lines_snapshot/new_lines_snapshot/start_line/end_line`，但 `document_store.apply_changes()` 会把全部 change 都应用掉。结果是：

- 文档状态是“全部变更后的状态”。
- 编辑历史却只记录了“第一处变更”。

这会让后续 location / generation 基于失真的 edit history 工作。VS Code 在多光标编辑、批量替换、某些格式化或 snippet 场景下都可能产生一次事件多个 `contentChanges`。现在的实现会在这些情况下给出错误 suggestion，或者把本不相关的修改误判成 rename/signature propagation。

Phase 1 如果暂时不支持 multi-change，至少应该在服务端直接 short-circuit：检测到 `len(changes) != 1` 时跳过 suggestion 管线，只同步文档状态，不要把错误样本写进 history。

### 3. “多步 rename” 检测缺少中间一致性校验，存在误报风险

文件：[/Users/xushengni/project/github/nextone/server/src/next_edit_server/location/engine.py](/Users/xushengni/project/github/nextone/server/src/next_edit_server/location/engine.py#L210)

`_try_rename_from_history()` 当前主要校验的是历史窗口首尾：

- `first.start_line == last.start_line`
- `first.old_lines` 和 `last.new_lines` 都是单行

然后把历史窗口第一条编辑的 `old_lines` 和最后一条编辑的 `new_lines` 合成一个 `EditRecord` 来做 rename 检测。核心问题在于它没有逐条验证中间 edit 是否与这次 rename 推断保持一致，几个薄弱点是：

- 没有逐条验证历史窗口里的所有编辑都发生在同一 `uri + start_line`。
- 没有要求这些编辑是连续输入同一标识符，而不是同一行上的多次独立修改。
- 没有检查中间编辑是否引入了其他结构性变化。

不过这一点的风险也不应表述得过重。当前实现还有两道后续过滤：

- 合成后的 `EditRecord` 仍然必须通过 `detect_rename()`，如果首尾拼不出有效的标识符重命名，会直接返回 `None`。
- 之后还要通过 `find_references()`，只有旧标识符在源码其他位置确实存在引用时才会继续生成 suggestion。

再加上历史窗口当前只有 3 条记录，这意味着它不是“只要首尾同行就一定会误报”，而是“在缺少中间一致性校验的情况下，仍然存在把几次独立编辑误拼成 rename 的风险”。这个策略确实修复了一类真实的多步输入 rename 场景，但也会在用户连续修改同一行不同内容时引入额外误建议可能性。

更稳妥的做法是增加连续性约束，例如：

- 历史窗口内所有 edit 都必须在同一 `uri + start_line`。
- 中间每步只允许单行、局部文本演化，不允许跨 token 结构变化。
- 最好要求每步是前一状态到后一状态的逐步扩展，而不是任意首尾拼接。

### 4. 扩展配置项里的 `logLevel` 现在实际上不生效

文件：[/Users/xushengni/project/github/nextone/editors/vscode/src/extension.ts](/Users/xushengni/project/github/nextone/editors/vscode/src/extension.ts#L83)

`activate()` 里虽然读取了 `nextone.logLevel`，但真正构造 `serverArgs` 时写死成了 `DEBUG`：

```ts
const logLevel = config.get<string>("logLevel", "INFO");
...
const serverArgs = ["--stdio", "--log-level", "DEBUG", "--log-file", logFile];
```

这会让配置文档和实际行为不一致，也会让用户在日常使用中始终产生高噪声日志。这个问题不影响主功能，但属于明显的实现/配置偏差。

## 总体判断

当前实现已经具备“可演示、可本地验证”的 Phase 1 状态，但还没到“可以放心长期开着用”的程度。最需要优先修的是：

1. suggestion 渲染与清理绑定到具体 editor，消除残留高亮。
2. multi-change 事件先明确降级处理，避免把错误样本写进 history。
3. 收紧 composite rename 的触发条件，降低误报率。

这三项修完之后，Phase 1 的真实可用性会明显好很多。
